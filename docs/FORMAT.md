# Trip repository format

A traveller's private Git repository is the canonical store. The tool's database (`.tripwright/state.sqlite`, ignored by Git) is a rebuildable index, the outbox of writes not yet committed, jobs and their results; deleting it loses only writes that were received but not yet committed, and the tool reports that window (`state(view="sync")`, `oldest_unsynced_at`).

```
my-travel/
├─ tripwright.yaml              format, current_trip, default timezone (no secrets)
├─ README.md                    generated front screen (block B)
├─ AGENTS.md, CLAUDE.md, .claude/, .codex/, .agents/   agent files (block C; `tripwright init --upgrade` refreshes them)
├─ .gitignore, .gitattributes   journals merge as a union, generated files are regenerated by `tripwright sync`
├─ profile/
│  ├─ conversation.yaml         conversation defaults and user-stated concession orders
│  ├─ people.yaml               people of all trips: id, name, trips
│  ├─ items/<id>.yaml           long-term items (said as lasting), with origin: trip, message, time, speaker, nature
│  └─ materials.yaml            optional, maintained by the user: reusable materials {id, text, path, trip}
└─ trips/<trip>/                one folder per trip, the folder name is the plan's `id` (e.g. 2031-05-wien)
   ├─ README.md                 generated front screen of the trip
   ├─ trip.yaml                 plan metadata (below); only `id` before the first plan
   ├─ raw/<local date>/<UTC time>-<speaker>-<id suffix>.md   one message per file, never edited
   ├─ ledger/items|facts|checks|questions/<id>.yaml, ledger/decisions/<id>.md   one record per file; only status fields change
   ├─ ledger/carry/<id>.yaml    long-term entries imported into this trip: pending, confirmed or not_used
   ├─ ledger/journal/<UTC date>.jsonl   append-only: each change with the message it came from
   ├─ plan/places.yaml, plan/bookings.yaml, plan/days/<date>.yaml   the committed plan
   ├─ plan/versions.jsonl       append-only version ledger (everything but the plan, plus its digest)
   ├─ evidence/<date>/<id>.yaml  evidence records
   ├─ research/                 the user's own material; the tool never rewrites it
   └─ views/                    generated: today.md, days/, packs/ (for hosts without tools), index.md, decisions.md, memory.md
```

IDs are type, UTC date and six random characters (`I-261031-k3f9qa`), so two writers that create records offline do not collide. YAML files load back to exactly the values written (JSON, which is valid YAML, is used where YAML would change a value), so an index rebuilt from the files equals the one they came from. A version's plan is the `plan/` of the commit whose `Tripwright-Version` trailer names it; older plans come back from history.

**How writes reach the repository.** Every write tool call is one operation `OP-<date>-<random>` recorded in the outbox in the same database transaction as the write; the answer already uses it (state `received`). The committer writes the index into the files about every two seconds as one commit (one commit per new plan version), with `Tripwright-Op` and `Tripwright-Request` trailers, and pushes without force (`pending_sync`). When the canonical branch (`origin/main`, or the local branch without a remote) contains the commit, the write is `effective`; only then may the agent say it is saved. A rejected push or a newer head fetched by `tripwright sync` rebuilds the index from that head beside the live one, replays the operations that are not in it, and swaps the result in at once: messages never conflict, recorded changes run through the ledger again, a plan commit whose base version or ledger changed becomes `conflict` with a notice that every turn returns until a plan based on the new head is effective. A remote that cannot be reached leaves writes pending and retries with backoff; answers never wait for it.

**Edits outside the tool.** A changed plan file is a proposal: if all checks pass and no user-decided part moves, it becomes a version recorded as an external edit; otherwise the version stays, the edit stays in the working copy and the front screen says so. A changed generated file is overwritten by the next commit (said once); a changed message file is restored; a record file that no longer parses keeps its previous content in the index and is reported until fixed. `tripwright check` verifies that files parse, messages were never edited, and the generated files of the last commit equal what the tool regenerates from that commit (its tree, date, parent and trailers).

**Starting another trip.** `turn(new_trip=<trip>)` or `tripwright new-trip <trip>` (all earlier writes must be effective) switches `current_trip`, copies the active long-term items of `profile/` into the new trip with their origin, and lists people and materials as entries with status `pending`: they apply and are marked until the user answers in the conversation; `turn(record={"carry": [{"id", "status": "confirmed"|"not_used"}]})` records the answer. `views/memory.md` shows every entry, its words, where it came from, its status here and where it was last used.

## Plan data

The plan is a typed Trip document. `trip.yaml` contains `id`, `title`, full ISO `start`/`end`, IANA `timezone`, configurable `areas`, `people` (`id`, `name`), `default_pace` and hard group `budgets` keyed by currency. No date, region, person name or exchange rate is fixed in the implementation. Exports also carry `export_format: 1` and the committed `version`.

`places.yaml` stores each place once. Required fields are `id`, `name` (a reader-facing explanation), `name_local` (the exact local search name) and `area`. Optional details include kind, intended subjects, priority, reason, coordinates, opening text, price/source details, links, checked time, weather suitability and notes. Unknown details stay absent. A day references place IDs rather than repeating fixed descriptions or prices.

`bookings.yaml` stores one booking per ID, with full `date`, kind, description (`what`), holder IDs (`subject`) and status. Pending actions require `why_now`; contacts and reservations require a contact name. Optional due date, purchase channels, missed-departure rule and place reference remain here. Fares have a unique ID, segment, ticket, subject IDs, optional amount per person and currency. `included_in` and `alternative` exclude a row from totals; unknown and estimated amounts remain visible as uncertainty. Currencies are added separately and never converted using an implicit rate.

`days/YYYY-MM-DD.yaml` contains `date`, `title`, `area`, pace, optional base/sunset and at most three `plans`, the first recommended. Each plan has named tracks, each with explicit `subject` IDs. Blocks have unique `id`, HH:MM `start` and `end`, kind (`visit`, `travel`, `meal`, `flex`, `anchor`, `reserve`), and at least a place reference, alternatives (`options`) or explanatory text. Only anchor blocks may omit end. Certainty is `fixed`, `estimated` or `unknown`. Optional app actions, source, fare ID, transfer time, walking time, baggage holder and equipment stay on the relevant block. Split activities at midnight. Tracks belonging to the same person must not overlap, including overlaps across separate tracks of a candidate.

Hard nodes are a day's `anchors`: ID, local time, text, subjects, optional exact place, required buffer and known travel minutes, evidence references, consequence and alternative. A timing margin and the truth of a timetable are different checks: enough time does not prove that the train exists or runs that day. Evidence must match the exact branch and date, be current and support the particular fact. Missing, stale or synthetic evidence stays unverified.

The old format's `from`/`to`, `type`, `sure`, `who`, `app`, `fare` and `anchors` map to these typed fields; `全组` becomes the actual participant ID set. Region enums, MM-DD dates, person-specific constants and fixed currency conversions have been removed. The former Markdown body sections become day notes, rain plans and candidate references. Publication-specific images, offers and trail cards are deferred to the views stage.

The ledger records keep their stored shape: items (scope with optional ISO start/end, HH:MM time_from/time_to, hierarchical place, channel; `*` means unrestricted; quote, reason, strength, source with the message's actual nature; `always` for principles, `long_term` for lasting entries), facts, decisions (options, choice, provenance, revisit conditions, locks with their placement snapshot), pending checks and undecided questions. Contexts, drafts, jobs, results, the outbox and notices are runtime state in the database only.

`tripwright init <folder> --from-db <db>` writes a single-database trip into a new repository, one commit per version. The older directory export (`tripwright export`) remains an audit snapshot for single-database use; import still validates its derived `verification` blocks and never certifies a candidate.
